## 二、我们要解决的问题

深远海养殖场离岸很远，人不能常驻。现在的困难是：

- 设备牌子杂，接口都不一样，管起来费劲
- 通信不稳定，动不动断线
- 出了问题只能靠人盯着，发现慢、处理更慢
- 很多"信息化系统"只是把数据画成图，**能看见问题，但管不住问题**

### 我们和别人的区别在哪（这句话最重要）

> **别人做到"我把命令发出去了"，我们做到"我知道设备到底动没动"。**

听起来差别不大，其实是**看板**和**控制系统**的分界线。这是全项目的核心，答辩时主打这句。

## 三、产品分四大板块

```
深远海养殖与海洋牧场智能管控平台
│
├── 鱼类 ────── 行为识别、生物量统计、生长模型与预测、鱼群分布与热力图   （4 项）
├── 环境 ────── 海况、水质                                            （2 项）
├── 结构安全 ── 灾害预警、能源保障                                     （2 项）
└── 智能 ────── 自动投喂、智能补光                                     （2 项）
```

### 平台要有的三个用处

| 用处 | 大白话 |
|---|---|
| **数据整理** | 把各处来的数据收拢到一起，整整齐齐放好 |
| **可视化** | 把数据画成图，一眼看明白现在什么情况 |
| **远程操控设备** | 人不用到现场，在网页上就能给设备下命令 |

### 两种"分法"的关系（容易绕晕，先记住这个）

| 分法 | 用来干什么 |
|---|---|
| **四大板块** | 做**网页菜单** —— 用户看到什么 |
| **四层流程**（接入 → 研判 → 处置 → 确认） | 做**数据怎么流** —— 后台怎么运转 |

**一句话**：板块管"用户看到什么"，四层管"数据怎么走"。两者不冲突。

## 四、核心：闭环是什么意思

### 一条命令的完整旅程

```
① 数据进来  →  ② 判断有没有问题  →  ③ 决定怎么处理
                                          ↓
⑥ 留下记录  ←  ⑤ 收到设备回执  ←  ④ 把命令发出去
```

**最关键的是 ⑤ 和 ⑥。**

大多数平台做到 ④ 就结束了："我发了命令"。但真正做控制的必须回答：

> **命令发出去了，可设备没动，系统知不知道？**

**我们的答案**：知道。命令超时没回执会自动重试，重试还不行就报警 —— **绝对不允许"悄悄地失败"**。

### 一条命令会经历哪些阶段

```
已创建 → 已发出 → 已收到回执 → 成功
                ↘ 超时 → 重试中 → 失败
                          ↘ 升级报警
```

| 阶段 | 意思 |
|---|---|
| 已创建 | 平台生成了这条命令 |
| 已发出 | 命令已经发给设备 |
| 已收到回执 | 设备回话说"我动了" |
| 成功 | 确认设备真的动了 |
| 超时 | 等太久没回话 |
| 重试中 | 再发一次 |
| 失败 | 重试几次还不行 → 报警 |

这套阶段表要能**在界面上看到**，答辩时直接展示，很有说服力。

### 安全底线（答辩一定会问）

| 情况 | 系统怎么做 |
|---|---|
| 环境指标越过安全线 | **规则说了算，AI 的意见被覆盖**（规则优先级最高） |
| 通信断了 | 进入"断连模式"：命令先存起来，恢复后补发并核对 |
| 命令超时没回执 | 自动重试 → 还不行就报警 → **通知到人** |
| 数据缺失或置信度低 | 界面明确显示"当前是建议模式"，不自动执行 |
| 任何异常 | 一键急停，**急停这条路不经过 AI、不经过网络** |

**对外统一说法**：我们做的是 **"决策辅助 + 受限自动执行 + 全程留痕"**，不是"全自动 AI 养殖"。
**主动说边界，评委就少一个攻击点。**

## 五、技术怎么做

### 四层结构

```
┌────────────────────────────────────────────────┐
│ ④ 网页前端   总览大屏 / 各板块页 / 告警 / 处置 / 追溯 │
├────────────────────────────────────────────────┤
│ ③ 后台服务   接口 · 规则引擎 · 决策 · 告警 · 调度   │
│              数据库（存指标、存业务记录）           │
├────────────────────────────────────────────────┤
│ ② 接入层     协议网关（Modbus/MQTT/HTTP）         │
│              + 设备模拟器（能故意造故障）           │
├────────────────────────────────────────────────┤
│ ① 设备层     传感器 / 摄像头 / 增氧机 / 投饵机      │
│              （我们不做硬件，靠标准协议接进来或模拟） │
└────────────────────────────────────────────────┘
```

**为什么把"接入层"单独拎出来**：

- 它是我们**没有硬件还能讲清"控制"**的技术依据
- 演示时**不依赖现场网络**（模拟器 + 本地服务可以完全离线跑）
- 以后真有设备了，只要加一个协议插件，平台主体不用改 —— **这就是"平台"的价值**

### 技术选型（按"5 个人 4 周能交付"来选）

| 位置 | 建议 | 为什么 |
|---|---|---|
| 前端 | Vue 3 + ECharts（或 React + ECharts） | 图表生态成熟，大屏效果容易做 |
| 实时刷新 | WebSocket | 比轮询体验好，实现不难 |
| 后台 | Python FastAPI 或 Node.js | **按团队会什么选**，不要为"先进"选没人会的 |
| 数据库 | PostgreSQL 或 SQLite | 演示场景单机 SQLite 完全够，**别上分布式** |
| 规则引擎 | 自己写个轻量的 | 不要引重框架，学起来比写起来慢 |
| 协议网关 | pymodbus / paho-mqtt + 自研模拟器 | 没硬件时，模拟器就是"设备" |
| 部署 | **一键启动脚本** | 现场演示必须一条命令起得来，而且要能离线 |

**明确不做（做了纯浪费时间）**：K8s、微服务拆分、MQTT 集群、消息队列、GraphQL。

### 接口约定（10-05 前必须定死）

| 接口 | 谁给谁 | 大概传什么 |
|---|---|---|
| 环境数据 | 接入层 → 后台 | 时间、塘口编号、水温、溶氧、盐度、浪高、风速 |
| 设备状态 | 接入层 → 后台 | 时间、设备编号、在线否、各项指标 |
| 下发命令 | 后台 → 接入层 | 命令号、设备号、动作、参数、超时时间 |
| 返回回执 | 接入层 → 后台 | 命令号、成功否、结果、实际时间、错误码 |
| 查当前状态 | 网页 ← 后台 | 汇总状态 + 风险等级 + 当前告警 |
| 查决策依据 | 网页 ← 后台 | 哪条数据触发的、命中哪条规则、结果如何 |

**接口文档必须写清 6 件事**（缺一项都算没写完）：
字段名、类型、**单位**、时间格式（统一毫秒数）、出错返回什么、一段示例数据。

> **单位是最容易出错的地方**：温度是摄氏还是华氏？长度是米还是厘米？**必须写清。**
> **同一个东西不许起两个名字** —— 你叫 `water_temp`、别人叫 `temp`，接口就对不上。

## 六、怎么证明我们做成了

> **规矩：每一个写进申报书的数字，都必须说得出是怎么测的。**

| 类别 | 指标 | 目标 | 怎么测 |
|---|---|---|---|
| **闭环** | 命令超时未回执的**检出率** | **100%** | 故意造故障测试（核心卖点，必须 100%） |
| **闭环** | 命令—回执成功率 | ≥ 98% | 日志统计 |
| **闭环** | 断线恢复后命令对账完整率 | **100%** | 断网 30 秒 / 5 分钟测试 |
| **速度** | 异常发生到报警的延迟 | ≤ 10 秒 | 注入已知异常，计时 |
| **稳定性** | 连续无人工干预运行 | ≥ 72 小时 | 挂机长跑 + 日志 |
| **数据** | 数据接入完整率（不丢点） | ≥ 99% | 上报数 vs 收到数 |
| **智能** | 风险分级准确率（对照人工标注） | ≥ 85% | 构造标注集 |
| **智能** | 报警误报率 | ≤ 10% | 长跑统计 |
| **扩展** | 新增一类设备接入的工作量 | ≤ 1 人日 | 记录实际工时 |
| **好用** | 从报警到处置完成的点击次数 | ≤ 3 次 | 数点击 |
| **可追溯** | 历史决策能完整回溯的比例 | **100%** | 随机抽 20 条反查 |

## 九、写在墙上的 7 条原则

1. **闭环比花哨重要**：一个"命令发出→回执确认→异常可追溯"的真闭环，胜过十个画出来的模块。
2. **没有硬件不是缺陷，是定位**：我们管的是协议、逻辑和可靠性，不是电机。
3. **P0 没做完，P2 不许动手**：数字孪生、手机端永远排最后。
4. **每个指标都要能测**：写进申报书的数字，必须说得出测量方法。
5. **现场不依赖网络、不依赖外设、不依赖临时安装**。
6. **主动讲局限**：答辩时先说边界，评委就少一个攻击点。
7. **不绑硬件、可追溯、不静默失败** —— 这三条是平台的立身之本。
